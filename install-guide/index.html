Installation guide

Installing, updating and running Reactive Shop

How to get the shop running on your server with Docker, the ready-built jar or from source, how to connect each supported database, how to update to a new version without losing anything, and answers to common questions.

Docker

The shop and a MariaDB database in two commands.

Ready-built jar

Java 21 and a database you already run.

Updating

Back up, replace, start. The database is upgraded for you.

FAQ

Setup token, safety checks, lost passwords, domains.
Other guides in this folder. Once the shop runs, connect payments, email and Google sign-in with the setup guide, and read PRODUCTION_TRANSFER.md before opening the shop to real customers.
1

What you need

A server that can run a Java program, and a database.

  • A server you can run programs on: a VPS or dedicated server (Linux, Windows or macOS), a Docker host, or a platform that runs Docker images or Java. Ordinary shared PHP hosting can't run it: the shop is a Java program that keeps running and listens on its own port.
  • Java 21 (for example Eclipse Temurin 21), unless you use Docker, which brings its own.
  • A database: MariaDB, MySQL, PostgreSQL, Microsoft SQL Server or Oracle Database. The Docker setup includes MariaDB. H2 (built in, in memory) is there for trying the shop out only.
  • Internet access during setup, to activate your purchase code. After activation the shop never needs the license server again.
  • For a public shop: a domain and HTTPS, usually through a reverse proxy such as Nginx or Caddy (see PRODUCTION_TRANSFER.md). Payment providers only call back to public https addresses.

Choose how to run it

All three end at the same setup wizard in your browser.

Docker Easiest

The shop plus its own MariaDB.

  • Needs Docker with Compose
  • No Java or database to install
  • Data kept in Docker volumes

Ready-built jar

reactive-shop.jar from the download.

  • Needs Java 21
  • Use a database you already run, any supported engine
  • Run it as a service (systemd, Windows service)

From source

Build the jar yourself.

  • Needs Java 21 (Maven comes with the wrapper)
  • For changing the code
  • Produces the same jar
3

Install with Docker

Starts the shop and a MariaDB 11.4 database next to it.

  1. Unzip the download and open a terminal in its folder (the one with docker-compose.yml).
  2. Create your settings file from the example: 
    cp .env.example .env
    Open .env and set DB_PASSWORD and DB_ROOT_PASSWORD to two long random passwords. Set SHOP_PUBLIC_URL to the address shoppers will use (e.g. https://shop.example.com, no trailing slash), and SHOP_PORT if port 8080 is taken.
  3. Build and start: 
    docker compose up -d --build
    The first build downloads Maven and the libraries and takes a few minutes.
  4. Find the setup token in the log (look for needs setting up): 
    docker compose logs app
  5. Open http://localhost:8080 (or your server's address) and follow the setup wizard. The database step is skipped: the shop is already connected to its MariaDB.
Where the data lives. The database is in the db-data volume. Everything the shop writes itself (generated secrets, saved integrations, storefront settings, uploaded images) is in the app-data volume, mounted at /app/data. Keep both when you update; back both up.
Behind a reverse proxy? Set SHOP_FORWARD_HEADERS=framework in .env only when the shop's port is reachable through the proxy alone, so visitors can't forge their IP address.
4

Install with the jar

For a server with Java 21 and a database you manage yourself.

  1. Check Java: java -version must say 21 or later.
  2. Make a folder for the shop, for example /opt/reactive-shop, and copy reactive-shop.jar into it. The shop keeps its own files in the folder it's started from, so always start it from this folder.
  3. Optionally create an empty database and a user for the shop. You can also let the wizard create the database.
  4. Start it: 
    cd /opt/reactive-shop
java -jar reactive-shop.jar
    The log prints the setup token (look for needs setting up).
  5. Open http://your-server:8080. If no database is reachable, the wizard asks for one; see Engine by engine. To connect it up front instead, set two URLs before starting.

Keep it running

Run the shop as a service so it starts on boot and restarts after a crash. A complete systemd unit file (Linux) is in PRODUCTION_TRANSFER.md, section 8; put your environment variables in the .env file it reads, and set WorkingDirectory to the shop's folder. On Windows, any service wrapper that runs java -jar reactive-shop.jar in the shop's folder works (for example WinSW or NSSM).

5

Build from source

Only needed if you change the code. Java 21 is all you install.

# Linux / macOS
./mvnw clean package -DskipTests
# Windows
mvnw.cmd clean package -DskipTests

The wrapper downloads Maven on first use. The jar is written to target/reactive-shop-<version>.jar; copy it to your shop folder and run it as in section 4. Always build with clean: an old target/ folder can hold files from the previous version (see the FAQ).

Running the tests? Two of them start the shop against the database it's configured for and clear all orders. Point them at a throwaway database, never at a shop with real orders.
6

Databases

The shop creates all its tables and a demo catalog itself, on any supported engine.

Supported: MariaDB, MySQL, PostgreSQL, Microsoft SQL Server and Oracle Database, plus H2 in memory for trying the shop out. No minimum version is enforced; use a version its vendor still supports. MariaDB and PostgreSQL are the engines used most in development, so if you have a free choice, pick one of those. You can move the shop to another engine later under Admin → Database, which copies all the data across.

Prepare a database user

Give the shop its own user rather than root or postgres. Replace the password with a long random one.

MariaDB / MySQL

CREATE DATABASE reactive_shop CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'shop'@'localhost' IDENTIFIED BY 'change-me';
GRANT ALL PRIVILEGES ON reactive_shop.* TO 'shop'@'localhost';

PostgreSQL

CREATE USER shop WITH PASSWORD 'change-me';
CREATE DATABASE reactive_shop OWNER shop;

If the database doesn't exist yet, the wizard creates it, but then the user needs the right to create databases.

Engine by engine

What the wizard's database step asks for:

EngineWhat to enterNotes
MariaDB / MySQLhost, port 3306, database name, userThe database is created if missing (the user needs CREATE rights). MySQL is reached through the bundled MariaDB driver.
PostgreSQLhost, port 5432, database name, optional schema, userDatabase and schema are created if missing; an empty schema means public.
SQL Serverhost, port 1433, database name, user (a SQL Server login)The database is created if missing. TCP/IP must be enabled on the server.
Oraclehost, port 1521, service name (e.g. FREEPDB1), userThe service must exist. The tables go into the signing-in user's own schema, so give the shop a user of its own.
H2a nameIn memory, inside the shop: everything is lost when it stops, admin account included. For trying the shop out only.
Try SQL Server and Oracle on a copy first. They are supported, but have had far less use than MariaDB and PostgreSQL. Test your setup on a staging copy before taking orders on them.

Skipping the wizard's database step

Set two connection URLs before the first start: the R2DBC one the shop uses, and the JDBC one for the database upgrades (Flyway). Use the same database, user and password in both.

# MariaDB or MySQL
SPRING_R2DBC_URL=r2dbc:mysql://localhost:3306/reactive_shop
SPRING_FLYWAY_URL=jdbc:mariadb://localhost:3306/reactive_shop

# PostgreSQL (add ?currentSchema=shop to both to use another schema)
SPRING_R2DBC_URL=r2dbc:postgresql://localhost:5432/reactive_shop
SPRING_FLYWAY_URL=jdbc:postgresql://localhost:5432/reactive_shop

# SQL Server
SPRING_R2DBC_URL=r2dbc:mssql://localhost:1433/reactive_shop
SPRING_FLYWAY_URL=jdbc:sqlserver://localhost:1433;databaseName=reactive_shop;encrypt=false

# Oracle
SPRING_R2DBC_URL=r2dbc:oracle://localhost:1521/FREEPDB1
SPRING_FLYWAY_URL=jdbc:oracle:thin:@//localhost:1521/FREEPDB1

# And for any engine:
SPRING_R2DBC_USERNAME=shop
SPRING_R2DBC_PASSWORD=change-me
SPRING_FLYWAY_USER=shop
SPRING_FLYWAY_PASSWORD=change-me

For MySQL, the JDBC URL starts with jdbc:mariadb:// too: the shop ships the MariaDB driver for both.

7

The setup wizard

Opens by itself on a new shop, at /setup.html. Until it's finished, every page leads there.

  1. Setup token. Proves you own the server. It's printed in the log when the shop starts (look for needs setting up), or set your own with SHOP_SETUP_TOKEN.
  2. License. Your CodeCanyon purchase code (Downloads → Reactive Shop → License certificate & purchase code) and the domain the shop will run on. One code covers one live domain; localhost, private IP addresses, *.test, *.local, *.localhost and staging., stage., dev. or test. subdomains are always free, so you can keep a test copy.
  3. Database, only if the shop couldn't reach one: see Engine by engine. The shop creates the tables and the demo catalog.
  4. Shop name and admin account. Your name, email and a password of at least 12 characters. You're signed in as the admin at the end.

Once finished, the wizard is gone for good. Next, connect payments and email with the setup guide, and replace the demo products under Admin → Products.

Automated deployments can create the first admin without the wizard: set both ADMIN_EMAIL and ADMIN_PASSWORD (12+ characters) before starting.

Files the shop keeps

Written next to the shop, in the folder it's started from (/app/data in Docker).

FileWhat's in itLose it and…
shop-install.propertiesGenerated secrets (JWT signing key, the key that encrypts saved credentials), the license, "setup finished"Everyone is signed out, saved payment and email credentials can't be read, and the license must be activated again. Back it up and keep it private.
active-database.propertiesThe database chosen in the wizard or under Admin → DatabaseThe shop starts on the default database from its configuration instead.
integration-settings.jsonSettings saved under Admin → Integrations (secrets encrypted)Payment, email and sign-in settings have to be entered again.
storefront-settings.jsonStorefront layout and content from Admin → StorefrontThe storefront goes back to its defaults.
uploads/Product images you uploadedThose images are gone.

Start the shop from a different folder and it won't find these files: it behaves like a new install.

9

Updating to a new version

Back up, replace the program, start it. The database is upgraded automatically on start.

Each version carries the database changes it needs (Flyway migrations). When the new version starts, it applies the ones your database doesn't have yet, in order, and records them in the flyway_schema_history table. You never run SQL scripts by hand, and your products, orders, customers and settings stay. You don't need to activate your license again.

Back up first

  1. The database. For example: 
    # MariaDB / MySQL
mysqldump -u shop -p --single-transaction reactive_shop > reactive_shop-backup.sql
# PostgreSQL
pg_dump -U shop -d reactive_shop -F c -f reactive_shop-backup.dump
# Docker (bundled MariaDB)
docker compose exec db sh -c 'mariadb-dump -u root -p"$MARIADB_ROOT_PASSWORD" --single-transaction reactive_shop' > reactive_shop-backup.sql
    For SQL Server and Oracle use their own backup tools (a .bak backup, Data Pump).
  2. The shop's files: the whole shop folder (the files listed above), or in Docker the app-data volume.
  3. Read the release notes of the new version for anything special.

Docker

  1. Unzip the new version and copy its files over your current folder. Keep your .env.
  2. Rebuild and restart: 
    docker compose up -d --build
    The volumes (db-data, app-data) are kept. Never run docker compose down -v: -v deletes them.
  3. Check the log: docker compose logs app.

Jar

  1. Stop the shop (e.g. sudo systemctl stop reactive-shop).
  2. Replace reactive-shop.jar in the shop folder with the new one. Leave every other file there as it is.
  3. Start it again from the same folder, and watch the log until it says the shop has started.

From source

If you changed the code, merge your changes into the new version first. Then build with clean:

./mvnw clean package -DskipTests

and replace the jar as above. Skipping clean can leave the previous version's migration files in target/, and the shop then refuses to start (see the FAQ). Don't edit or delete migrations that have already run on your database; add new ones with a higher version number instead.

If something goes wrong

Going back to an older version over an upgraded database isn't supported. Stop the shop, restore the database backup and the shop's files, and start the old version. Then send the error from the log to support.

10

FAQ

Where do I find the setup token?

In the shop's log, right after it starts: look for Reactive Shop needs setting up. With Docker: docker compose logs app; with systemd: journalctl -u reactive-shop. To choose it yourself, set SHOP_SETUP_TOKEN before starting.

The shop stops at startup with "Refusing to start in production".

A safety check found an unsafe setting, and the message names it: a JWT_SECRET shorter than 32 characters, an ADMIN_PASSWORD shorter than 12 characters or admin123, or SHOP_CORS_ALLOWED_ORIGINS containing * or localhost. Fix that setting, or leave it unset (secrets are then generated for you). Details: PRODUCTION_TRANSFER.md, section 4. Set SHOP_PRODUCTION=false only on your own development machine.

The wizard can't connect to my database.

Check host, port, user and password from the server the shop runs on (not your own computer): a firewall, a database that only listens on 127.0.0.1, or a user that may only connect from localhost are the usual causes. In Docker, the database's host name is its service name (db), not localhost. SQL Server needs TCP/IP enabled; Oracle needs the exact service name.

The license step says my code is already in use.

A code covers one live domain. Moving the shop? On the old shop, open Admin → Settings → License and deactivate it, then activate on the new one (allow up to a minute in between). Test and staging addresses (listed in the wizard section) don't count.

I forgot the admin password.

With email set up, use Forgot your password? on the sign-in page. Without email: stop the shop, set ADMIN_EMAIL to a new address and ADMIN_PASSWORD to a strong password, and start it again. That creates a second admin (an existing address is never changed). Sign in with it, remove the two variables, and set up email so the old account can use Forgot your password?, or make it a customer under Admin → Users.

How do I run it on another port?

Set SERVER_PORT (e.g. SERVER_PORT=8090) for the jar, or SHOP_PORT in .env for Docker. Update SHOP_PUBLIC_URL to match if shoppers reach the shop directly on that port.

A payment method doesn't show at checkout.

Each method stays off until its credentials are saved and Offered at checkout is on under Admin → Integrations. See the setup guide.

Can I use H2 for a live shop?

No. H2 keeps everything in memory and loses it, admin account included, whenever the shop stops. Use it to look around, then install on a database server.

Can I switch databases later?

Yes: Admin → Database copies all the data to another engine and switches the shop over. Back up first, and test the new database before taking orders on it.

How do I remove the demo products and test orders?

Edit or delete products under Admin → Products. Restart store fresh (Admin → Overview) deletes all orders, payment records and carts and returns their stock, but keeps products and customers.

After updating, the shop won't start: "Found more than one migration with version …"

The build folder still holds the previous version's migration files. Rebuild with ./mvnw clean package (the clean matters). The ready-built jar from the download never has this problem.

Can it run on shared hosting (cPanel, PHP)?

No. It needs a server where a Java 21 program (or a Docker container) can run continuously and listen on a port: a VPS, a dedicated server, or a container platform.

Do I need to keep anything secret?

shop-install.properties, integration-settings.json, your .env and your database backups. Never put them in a public place or a public Git repository.
